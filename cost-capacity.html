01 · Unit economics

Start with cost per useful outcome

Monthly cloud spend is too aggregated to guide engineering decisions.

cost / successful task = total serving + retrieval + tools + infra cost ÷ successful tasks

Cost/request

Useful for chat/API traffic.

Cost/1M tokens

Useful for model/provider comparisons.

Cost/success

Best when retries and quality differ.

02 · Token economics

Tokens are both a cost unit and a capacity unit

Long prompts consume prefill compute, context/KV capacity and provider spend.

request cost ≈ input_tokens × input_price + output_tokens × output_price + tool/retrieval/infra
Optimize the numerator and denominator: cheaper tokens are irrelevant if quality drops enough to create retries or human escalation.
03 · Capacity

Concurrency is the bridge between demand and hardware

A service can have excellent tokens/sec in a benchmark and still fail under real concurrent load.

Arrival rate→Queue→Concurrent work→Throughput
capacity planning asks: peak demand × service time × safety margin
04 · Batching economics

Batching trades latency for utilization

Combining work increases GPU efficiency until memory pressure, queue delay or scheduling contention dominates.

Optimize forLikely bias
Interactive chatTTFT and tail latency
Offline batchMaximum throughput / GPU-hour
Agent workloadsEnd-to-end task latency + tool waits
High-volume APICost/request under SLO constraints
05 · GPU economics

Pay for useful GPU time, not allocated GPU time

Idle accelerators can dominate cost in self-hosted systems.

Reserved / committed

Good when baseline demand is stable and utilization is predictable.

On-demand / elastic

Good for experiments, spikes and uncertain demand.

Watch: GPU utilization alone is incomplete. Measure useful tokens/sec, queueing, memory occupancy, failed requests and SLO attainment.
06 · Model routing

The cheapest model is often a routing decision

Not every request needs the largest reasoning model.

Request→Difficulty / risk classifier→Small modelorLarge model
Escalation: use a cheaper default when confidence/risk allows, then escalate uncertain or high-value cases.

What to remember

Cost & capacity 80/20

Economics and reliability are the same problem viewed from different sides of the queue.

Measure cost per successful outcome
Track input and output tokens separately
Capacity-plan for peaks, not averages
Include queueing in latency
Batch only within SLO limits
Measure useful GPU work
Route easy requests to cheaper models
Account for retries and tool cost
Use committed capacity only for stable baseline demand
Tie spend dashboards to quality metrics
