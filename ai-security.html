Module 19 · AI Security, Guardrails & Governance

Do not secure the model. Secure the system around it.

The 20% of AI security that explains 80% of production risk: treat model inputs and outputs as untrusted, minimize authority, enforce policy outside the model, isolate execution, protect data, and preserve evidence of every consequential action.

Master mental model

The LLM is a probabilistic decision component inside a security system

A model can misread instructions, follow malicious content, hallucinate an action, or produce unsafe arguments. The security architecture must assume that happens eventually.

The model may influence a decision, but deterministic controls own authorization and execution.
Security rule: never make “the model decided it was allowed” equivalent to authorization.
LLM-specific threat

Prompt injection is an instruction/data boundary failure

Direct injection

The user intentionally tells the model to ignore or override its intended instructions.

User → malicious instruction → model

Indirect injection

Malicious instructions are embedded in content the model reads: webpages, PDFs, emails, retrieved chunks, images, or tool output.

Attacker → external content → agent reads → behavior changes

OWASP treats prompt injection as a core LLM application risk, and explicitly notes that RAG or fine-tuning do not eliminate it. Browser/agent systems are especially exposed because every external artifact can contain adversarial instructions.

Crucial distinction: retrieved text is data about the world, not automatically trusted instructions for the agent.

Agency

Agent risk grows with functionality × permissions × autonomy

OWASP's excessive-agency framing is practical: damage depends less on how eloquent the model is and more on what the surrounding system lets it do.

Functionality

Does the agent have tools it does not actually need?

Permissions

Can those tools access more data or operations than the task requires?

Autonomy

Can the agent execute high-impact actions without independent checks?

blast radius ≈ capability × privilege × autonomy
Least privilege for agents: expose the smallest tool surface, narrowest resource scope, shortest credential lifetime, and lowest-impact operation that completes the job.
Containment

Sandbox the execution environment, not just the prompt

Filesystem boundary

Restrict readable/writable directories. Mount sensitive paths read-only or not at all.

Network boundary

Allowlist destinations. Prevent arbitrary outbound requests from becoming an exfiltration channel.

Process boundary

Limit shell commands, subprocesses, runtime duration, CPU, memory, and privileges.

Credential boundary

Inject scoped short-lived credentials only when required; do not expose broad secrets in context.

Sandboxing does not make the model trustworthy. It makes a model mistake less expensive.
Confidentiality

Do not put data in context unless the current decision needs it

Sensitive information disclosure can happen through prompts, retrieval, logs, model output, rendered links, tool calls, or accidental cross-user state.

Collect minimum→Classify→Filter / redact→Authorize retrieval→Log safely

PII / secrets

Mask, tokenize, or remove before model access when semantics permit.

Tenant isolation

Enforce access filters before retrieval, not after the model sees the chunk.

Logs

Trace enough for audit without turning telemetry into a second sensitive-data lake.

Identity & authorization

The agent inherits the user's authority: it never invents its own

Authentication

Who is this user or service?

Authorization

Is this identity allowed to perform this exact operation on this exact resource?

allow = user_can(action, resource) ∧ tool_is_allowed ∧ policy_passed

Do not authorize based on natural-language claims such as “the user said they are an admin.” Pass verified identity and scoped permissions from the application layer.

Confused-deputy defense: the model cannot grant itself authority simply because untrusted content asks it to.
RAG security

Your vector database is part of the attack surface

Poisoned knowledge

Malicious or compromised documents can manipulate answers or carry indirect injections.

Cross-tenant leakage

Similarity search can retrieve unauthorized content unless permissions are applied before or during search.

Embedding leakage

Embeddings are not a safe anonymization strategy. Treat the index as sensitive infrastructure.

Source spoofing

High similarity does not prove authenticity. Preserve document provenance and trust metadata.

Secure retrieval pipeline: authorize → filter scope → retrieve → preserve provenance → treat chunk text as untrusted evidence.
Supply chain

Models, adapters, prompts, tools, datasets, and MCP servers are dependencies

AI expands the software supply chain. A compromised model artifact, fine-tuning dataset, tool server, plugin, or prompt package can change behavior without touching your core application code.

Pin model / adapter versions
Verify artifact origin and hashes
Review third-party tool permissions
Track prompt and policy versions
Scan container and package dependencies
Separate dev/test/prod credentials
Adversarial evaluation

Red-team the system at its seams, not just the chatbot

SeamAttack question
PromptCan a user override intended behavior?
RetrievalCan poisoned content redirect the model?
Tool argumentsCan malformed output trigger dangerous execution?
AuthorizationCan the agent act outside the user's permissions?
NetworkCan it exfiltrate data to arbitrary destinations?
MemoryCan one user poison persistent state for another?
CostsCan loops cause unbounded token/tool consumption?
Test complete attack chains. A prompt injection that produces strange text is less important than one that reaches a privileged tool with executable arguments.
Governance

Governance converts security intentions into repeatable controls

NIST's Generative AI Profile frames risk management across the lifecycle. For engineers, the useful translation is: know the use case, assign ownership, document controls, measure them, and keep evidence.

Before deployment

Risk classify use case, define prohibited actions, map data, set approval boundaries, establish eval suites.

During operation

Monitor incidents, drift, permission use, data access, overrides, security evals, and control effectiveness.

policy → control → telemetry → evidence → review → improvement
Production blueprint

A defensible agent security architecture

Identity, policy, ACLs, and sandboxing remain deterministic. The model is inside the control plane, not above it.
What to remember

The AI security 80/20

Treat model input and output as untrusted
External content can contain indirect prompt injection
Never use prompts as access control
Minimize tool functionality, permissions, and autonomy
Authorize before retrieval and before execution
Sandbox filesystem, network, process, and credentials
Preserve provenance for retrieved evidence
Validate typed tool arguments deterministically
Require approval for high-impact irreversible actions
Audit identities, decisions, tool calls, and policy results

If you understand one sentence

The model should never be the security boundary. Put deterministic identity, authorization, policy, isolation, and audit controls between probabilistic reasoning and real-world effects.
