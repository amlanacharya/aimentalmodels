Module 19 · Application layer

AI Application Backend & API Engineering

Ordinary CRUD assumes short requests. AI applications wait on models, retrievers, tools and humans; stream partial results; create expensive work; and often outlive the original HTTP request. This module is the 20% of backend engineering that explains 80% of those differences.

01 · Different workload

An AI request is not a normal CRUD request

A database lookup might finish in milliseconds. An LLM request can stream for seconds, call multiple tools, retry, wait in a queue, or continue after the client disconnects.

CRUD-shaped request

HTTP→DB→JSON

Usually short, bounded and transaction-like.

AI-shaped request

HTTP→Retrieve→Model→Tools→Stream

Long-lived, multi-stage, variable-cost and partially observable while running.

Pareto cut: design around waiting, cancellation, partial progress, overload and replay—not only request/response serialization.
02 · Async I/O

Concurrency is mostly about not wasting waits

When a request awaits a model API, vector database, object store or tool, the server can work on another request instead of blocking an entire worker.

I/O-bound

Network calls, DB queries, object storage, remote model calls.

Use: async I/O where the library supports it.

CPU-bound

Heavy parsing, compression, local inference, image transforms.

Use: processes, worker pools, native kernels or dedicated services.

GPU-bound

Model execution itself.

Use: a serving engine and its scheduler; do not treat GPU work like ordinary web-thread work.
async ≠ faster computation async = do useful work while another operation is waiting
03 · Streaming

SSE by default; WebSockets when the conversation is truly bidirectional

Token generation naturally produces a one-way stream from server to browser after the client sends a request.

PatternBest fitMental model
SSEToken streams, progress events, status updatesClient opens stream; server pushes events over HTTP
WebSocketReal-time bidirectional control, voice sessions, collaborative interactionsBoth sides keep sending messages on one connection
PollingSimple background-job statusClient periodically asks whether work is done
WebhookServer-to-server completion notificationJob finishes later and calls a registered endpoint
Rule: do not choose WebSockets just because output is “real time.” One-way model output is often simpler with SSE.
04 · Concurrency

Unlimited concurrency is an outage generator

Your web server may accept thousands of connections while the downstream model can only run tens or hundreds efficiently. The gap must be controlled.

Admission control belongs before the constrained dependency.

Concurrency limit

Caps how many expensive operations are in flight.

Queue limit

Caps how much waiting work you are willing to accumulate.

05 · Queues

If work should survive the HTTP request, make it a job

Research agents, document ingestion, batch embeddings, long evaluations and report generation should often be durable jobs rather than fragile open requests.

POST /jobs→Persist job→Queue→Worker→Result store

Request path

Validate → authorize → create job → return job ID quickly.

Worker path

Claim → execute → checkpoint → retry or dead-letter → persist result.

06 · Backpressure

When downstream slows, upstream must feel it

Backpressure prevents a temporary slowdown from becoming an infinite queue, memory spike or retry storm.

Bounded queues

Stop accepting unlimited work.

Load shedding

Reject low-priority work early when capacity is exhausted.

Timeout budgets

Do not let every stage consume the full request timeout independently.

request budget = queue wait + retrieval + model + tools + stream overhead
07 · Rate limiting

Protect by cost, not only request count

One 200k-token request is not equivalent to one 20-token request. AI limits often need multiple dimensions.

LimitProtects
Requests / minuteAPI control plane
Concurrent generationsModel capacity
Input/output tokensCost and GPU time
Tool calls / runExternal systems and runaway agents
Jobs / tenantFairness across customers
08 · Retries & idempotency

Retry reads freely; retry side effects carefully

Transient model or network failures justify retries. Payments, emails, ticket creation and database mutations can duplicate consequences.

Idempotency key

A stable operation ID lets the server recognize a replay and return the previous outcome instead of executing twice.

same tenant + same idempotency key → same logical operation

Retry policy

Use exponential backoff + jitter, cap attempts, and distinguish retryable from permanent errors.

Agent rule: tool retries need operation identity, not blind loop repetition.
09 · Caching

Cache deterministic work before stochastic work

Caching is powerful when the inputs and validity rules are clear.

Good cache candidates

Embeddings, parsed documents, retrieval results, tool metadata, auth claims.

Conditional candidates

LLM responses when prompt/model/temperature/context and business freshness rules permit reuse.

Danger

Serving stale permissions, policies, prices or personalized context from a poorly keyed cache.

cache key should include every input that can change the correct result
10 · Connection pools

Every dependency has finite sockets, connections and workers

Async code can create far more concurrent tasks than your database, Redis, vector store or HTTP pool can safely serve.

Pareto cut: tune application concurrency together with downstream connection pools. A 500-request semaphore is useless if the DB pool has 20 connections and every request needs one.
11 · Auth & tenancy

Carry identity through every AI hop

The user’s authorization context must survive retrieval, tool use, background jobs and caches.

Identity→API auth→Tenant policy→Retrieval filter→Tool scope

Security boundary

Never rely on the prompt to say “only access documents the user can see.” Enforce tenancy and authorization in deterministic backend code.

12 · API shape

Expose the lifecycle, not implementation internals

Interactive generation

POST /responses → stream events → client may cancel

Good for chats, copilots and short agent runs.

Durable job

POST /jobs → 202 + job_id GET /jobs/:id GET /jobs/:id/events POST /jobs/:id/cancel

Good for long research, ingestion, evaluation and batch work.

Design principle: separate task identity from connection identity. A network connection may die; the logical task may still exist.
13 · Reference architecture

A practical AI application backend

Keep admission control, durable work, state, model access and observability as explicit backend responsibilities.
What to remember

The backend/API 80/20

Use async for I/O waits, not CPU magic
Prefer SSE for one-way token streaming
Bound concurrency around scarce dependencies
Use durable jobs for long-running work
Implement backpressure and load shedding
Rate-limit by cost as well as requests
Use idempotency for side-effecting retries
Key caches with freshness and authorization in mind
Tune connection pools with app concurrency
Carry tenant identity through retrieval and tools
Separate logical task IDs from network connections
Trace every expensive backend stage

If you understand one sentence

An AI backend is a flow-control system around slow, expensive and sometimes long-lived probabilistic work.
