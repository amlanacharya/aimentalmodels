Module 13 · Distributed AI Systems

Networking, clusters & distributed LLM inference

Why large-model serving becomes a distributed-systems problem: collectives, topology, RDMA, prefill/decode disaggregation, KV movement, expert traffic, routing, autoscaling, and where llm-d fits above engines such as vLLM and SGLang.

01 · Why distribute?

One GPU stops being the whole computer

Once weights, KV cache, activations, or request volume exceed a single device, performance depends on how work and data move between devices, not just how fast each GPU is.

Capacity

The model or cache does not fit on one accelerator.

Throughput

One replica cannot serve enough concurrent traffic.

Specialization

Different workers can optimize different phases such as prefill and decode.

The mental model: distributed AI is mostly a question of what must communicate, how often, and how expensive that communication is.
02 · Network intuition

Latency and bandwidth are different bottlenecks

Latency

How long it takes before a transfer starts completing. Small frequent messages are latency-sensitive.

time ≈ startup latency + bytes / bandwidth

Bandwidth

How many bytes can move per second once the pipe is busy. KV transfers and large collectives are bandwidth-sensitive.

5.0 ms25 GB/s fabric + startup
1.5 ms100 GB/s fabric + startup
bandwidthdominant concern

Illustrative only; real performance depends on protocol, topology, contention, serialization, and hardware.

03 · Collectives

Distributed training repeatedly asks GPUs to agree

Libraries such as NCCL implement high-performance collective communication patterns used to move tensors between accelerators.

All-reduce

Combine values across workers and return the result to every worker. Common for gradient synchronization.

All-gather

Each worker contributes a shard; everyone receives the complete set.

Reduce-scatter

Combine values while leaving each worker with only its shard: useful in sharded training.

Ring-style collectives trade many coordinated transfers for high link utilization.

Who is connected to whom matters

Cluster topology becomes part of model performance. A parallelism strategy that looks good on paper can collapse if it creates too much traffic across slow links.
05 · Distributed training

Parallelism means choosing what dimension to split

Data parallel

Replicate the model, split examples, synchronize gradients.

Tensor parallel

Split individual matrix operations across GPUs; communication happens inside layers.

Pipeline parallel

Different groups own different layer ranges; microbatches move through stages.

Expert parallel

MoE experts live on different devices; tokens must be routed to the devices hosting selected experts.

parallelism win = saved compute / memory − communication − synchronization − idle time
06 · Distributed inference

Serving has a different communication shape

Inference adds request routing, KV-cache locality, queueing, prefix reuse, heterogeneous sequence lengths, and strict tail-latency goals.

Gateway→LLM-aware router→Model workers↔KV / interconnect

Replica scaling

Multiple independent replicas increase throughput but each replica owns its own weights/cache.

Distributed model

One request can span several accelerators through tensor, pipeline, or expert parallelism.

07 · Prefill / decode disaggregation

Separate the compute-heavy phase from the bandwidth-heavy phase

Prefill processes the prompt in parallel and tends to be compute-heavy. Decode generates one token at a time while repeatedly reading model state and KV cache, making it much more memory-bandwidth-sensitive.

Disaggregation can isolate long prefills from latency-sensitive decode, but now KV transfer and routing become first-class systems problems.
You only win if the network is fast enough. Moving KV state across nodes can erase the benefit of phase specialization if the fabric is too slow.
08 · llm-d

llm-d turns model servers into a distributed inference system

llm-d is an open-source Kubernetes inference-serving stack. It sits above engines such as vLLM and SGLang and adds cluster-level routing, cache awareness, disaggregation, autoscaling, and operational control.

Client→Gateway / proxy→llm-d Router + EPP→InferencePool→vLLM / SGLang workers

LLM-aware routing

Route using load, prefix-cache state, worker role, and scheduling policies instead of generic round-robin balancing.

Disaggregated serving

Select prefill and decode workers separately and coordinate KV-cache transfer between them.

Fleet-level KV thinking

Cache-aware routing, indexing, offload, and peer sharing turn KV from a per-process implementation detail into cluster state.

LayerPrimary job
vLLM / SGLangExecute the model efficiently on accelerator workers: batching, kernels, local KV management, decoding.
llm-dCoordinate many workers: LLM-aware routing, P/D orchestration, fleet cache locality, autoscaling, rollouts, multi-node serving.
Kubernetes / Gateway API ecosystemPlacement, lifecycle, networking primitives, service discovery, resource management.

The mental model

vLLM/SGLang optimize the engine; llm-d optimizes the fleet. It is especially relevant once inference moves from “run one server” to “operate a distributed pool under real traffic.”

09 · MoE & expert traffic

Conditional compute creates conditional network traffic

In expert-parallel MoE serving, a token may need to travel to another device to reach its selected expert, then return. The router therefore changes not only compute allocation but communication.

token → router → selected expert device(s) → expert output → combine
MoE can reduce active arithmetic without reducing communication complexity. Expert placement, load balance, all-to-all traffic, and hot experts become cluster-design concerns.
10 · Stragglers, queues & failure

The slowest worker can become everyone's problem

Stragglers

Synchronous operations often progress at the pace of the slowest participant.

Pipeline bubbles

Stages can sit idle waiting for work or downstream capacity.

Tail latency

Average throughput can look healthy while a small fraction of requests experience severe queueing.

Operational controls

Backpressure, admission control, routing, timeouts, retries, autoscaling, health isolation, and safe rollout policies.

Observability

Measure queue depth, TTFT, inter-token latency, cache hit rate, link utilization, transfer time, worker saturation, and p95/p99, not GPU utilization alone.

If you understand one sentence

At cluster scale, model performance is the product of compute, memory, network topology, routing, and synchronization—not GPU speed alone.
