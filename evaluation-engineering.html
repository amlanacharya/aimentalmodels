Module 08 · Measure what matters

Evaluation Engineering for LLMs, RAG & Agents

The 20% that prevents 80% of bad AI decisions: build representative eval sets, separate deterministic checks from subjective judging, evaluate each stage of a system, and treat production feedback as part of the eval loop.

01 · Start with the system

An eval is a measurement system, not a benchmark number.

A useful eval tells you whether a system improved, why it failed, and whether the gain survives realistic conditions.

Product goal→Representative tasks→Grader→Metric→Decision

Capability

Can the model or system perform the task at all?

Quality

How well does it perform relative to your rubric or baseline?

Reliability

How consistently does it succeed across slices, retries and production conditions?

Mental model: define the decision first. If the score cannot change a launch, rollback, routing or tuning decision, question why you are measuring it.
02 · The dataset is the product specification

Your golden set should look like production, not a demo.

Representative core

Use real task distributions: common queries, common documents, real tool combinations, real user phrasing.

Risk-weighted edge cases

Rare but expensive failures deserve deliberate coverage even when they are uncommon in traffic.

freeze a holdout set
tag examples by slice
keep hard negatives
record expected behavior
version datasets
add production failures back carefully

Do not optimize on your final test set.

If you repeatedly inspect failures and tune against the same examples, that set becomes development data. Maintain dev, holdout and production-monitoring layers.

03 · Use the cheapest reliable grader

Prefer deterministic checks whenever the task allows them.

04 · LLM-as-judge

An LLM judge is another model that must itself be evaluated.

Do not treat judge scores as ground truth. Treat them as a scalable approximation to a human rubric.

Position bias

A judge may prefer the first or second answer simply because of presentation order.

Style bias

Longer, polished or confident answers can be rewarded even when they are less correct.

Self / family bias

A judge may systematically favor outputs that resemble its own style or model family.

Audit the judge.

Create a human-labeled subset, measure judge-vs-human agreement, inspect disagreements, randomize answer order for pairwise grading, and keep the rubric concrete.

05 · Compare when absolute scoring is fuzzy

“Which answer is better?” is often easier than “score this from 1 to 10.”

same prompt→Answer AAnswer B→rubric + judge→A / tie / B

Why pairwise works

Relative differences are easier to distinguish than assigning globally consistent absolute scores.

Where it helps

Prompt comparisons, model upgrades, writing quality, answer usefulness and agent deliverables.

Good default: run candidates on the same examples, blind the model names, randomize left/right order, then report win/tie/loss with uncertainty.

07 · Agent evals

Score the trajectory, not only the final text.

Two agents can reach the same answer while one wastes calls, uses the wrong tools, violates policy, or gets lucky.

Outcome

Was the task completed correctly?

task successbusiness result

Trajectory

Were the intermediate decisions and tool calls sensible?

tool selectionargument correctnessstep count

Constraints

Did the agent remain within safety, cost and operational boundaries?

policylatencycost
state→decision→tool call→observation→next state
Agent eval principle: final success + process quality + constraint compliance. Any one alone can hide a serious failure mode.
08 · Repeated sampling

Pass@k asks whether at least one of k attempts succeeds.

This is especially useful for code or search-style tasks where you can generate multiple candidates and verify them.

Approximation under independent attempts: P(at least one success) = 1 − (1 − p)^k
30%single attempt
83%at least one success
+53 ppillustrative gain

This interactive uses the simple independence formula for intuition. Formal benchmark pass@k estimators account for finite sampled candidates.

Important: pass@k can improve dramatically with more samples even when pass@1 is unchanged. Always compare metrics at the same k and sampling setup.
09 · Every change needs a regression suite

A new model can improve the headline metric while breaking a critical slice.

Slice by behavior

Simple vs complex, known vs unknown, short vs long context, language, customer segment, tool availability, document type.

Gate releases

Define minimum acceptable thresholds for critical capabilities rather than optimizing one global average.

SliceOldNewDecision
Overall task success82%86%looks better
Long-context cases79%68%regression
Safety-critical cases96%91%block release

Illustrative example. Averages can hide regressions that matter more than the average improvement.

10 · Evals do not end at launch

Offline evals predict production; production tells you what the next eval should contain.

offline eval→canary / A-B→production traces→failure review→new eval cases

Offline

Fast regression checks, reproducible comparisons, controlled datasets.

Online

Real traffic, real latency/cost, user behavior, previously unknown failure modes.

The operating loop

Specify → Measure → Improve → Deploy → Observe → Add failures back to evals. Your eval suite should evolve as the system and its users evolve.

version model + prompt + tools
store traces with eval runs
compare candidates on same examples
measure uncertainty
audit LLM judges
track cost and latency alongside quality
