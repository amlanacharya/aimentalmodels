LLM Inference Optimization & Serving

You already know what the transformer computes. Now learn why two servers running the same model can differ massively in memory use, first-token latency, tokens/sec, and concurrent-user capacity.

01 · Start here

Optimization only makes sense after you know what is expensive.

LLM serving is a fight over three scarce resources: compute, memory capacity, and memory bandwidth. Different phases stress them differently.

Prefill

Process many prompt tokens in parallel. Large matrix multiplications dominate.

Think: compute-heavy, batch-friendly.

Decode

Generate one new token per sequence at a time while repeatedly reading weights and KV cache.

Think: memory-bandwidth-sensitive.

Concurrency

Each active sequence carries KV-cache state. More users means more live memory.

Think: memory-capacity pressure.

The Pareto diagnostic

slow first token?→look at prefill·slow generation?→look at decode·low concurrency?→look at KV memory
02 · Attention kernels

FlashAttention: same attention, less memory traffic.

The key idea is not “approximate attention.” FlashAttention computes exact attention while changing how the work is tiled so intermediate data does not bounce unnecessarily between GPU memory levels.

Naive mental model

QKᵀ→write big score matrix→softmax→read again

Long sequences make that intermediate attention matrix expensive to materialize and move.

FlashAttention mental model

tile Q/K/V→compute on-chip→write less to HBM

The algorithm is IO-aware: reduce reads/writes between high-bandwidth memory and faster on-chip memory.

Mental model: FlashAttention speeds attention mainly by reducing memory movement, not by changing the mathematical result.
03 · Shrink the representation

Quantization trades numerical precision for memory and speed.

Weights stored in fewer bits require less memory and less bandwidth. That can make a model fit on smaller hardware and often increases inference throughput, but quality and kernel support matter.

04 · Keep the GPU busy

Batching improves throughput by sharing hardware across requests.

A GPU waiting on one sequence is wasted capacity. Serving engines combine work from multiple sequences so matrix operations become larger and utilization rises.

Static batching

Group requests, run the batch, wait for all of them to finish.

Problem: one long request can hold the batch hostage.

Continuous batching

Admit new work as sequences finish instead of waiting for a whole batch boundary.

Result: better GPU utilization for mixed-length online traffic.
Illustrative, not benchmark data. Larger batches usually improve total throughput until saturation, while queueing and per-request latency can rise.

05 · Manage KV memory

Paged KV cache attacks fragmentation and wasted capacity.

Naively reserving one large contiguous KV region per sequence is awkward when requests have unpredictable lengths. Paged approaches manage KV memory in smaller blocks.

Mental model: paged KV management lets the server pack many variable-length sequences more efficiently instead of over-reserving large contiguous regions.
06 · Predict more than one token

Speculative decoding tries to break the one-token-at-a-time bottleneck.

A cheaper drafter proposes several future tokens. The target model verifies them in parallel. Accepted tokens let you advance multiple positions with fewer expensive target-model decode steps.

draft model proposes→A · B · C · D→target verifies together→accept prefix

Works best when

The drafter predicts what the target would have produced often enough that acceptance is high.

Can disappoint when

Draft overhead is high, acceptance is low, or the baseline model is already efficiently saturated.

Mental model: speculative decoding is useful only if drafting + verification costs less than ordinary sequential target-model decoding.
07 · Sparse models

MoE: lots of parameters, only some experts active per token.

Mixture-of-Experts models separate total parameters stored from parameters activated for a token. A router selects a small subset of experts.

token hidden state→router→expert 3expert 11→combine
Critical serving insight: sparse activation reduces compute per token relative to activating every parameter, but you may still need memory for a very large expert weight set. Multi-GPU expert placement and communication can become the systems problem.
08 · Pick the serving engine

llama.cpp, vLLM, and SGLang solve overlapping, but not identical, problems.

EngineNatural fitPareto mental model
llama.cppLocal inference, consumer hardware, CPU/GPU hybrid, GGUF and aggressive quantization.Make one machine run models remarkably efficiently and portably.
vLLMHigh-throughput GPU serving, OpenAI-compatible APIs, continuous batching, production inference.Maximize serving efficiency across many concurrent sequences.
SGLangHigh-performance serving plus structured/agentic workloads and cache-aware execution.Optimize repeated structured generation and shared prefixes as a runtime problem.

Do not memorize brands. Memorize the selection axes.

single-user vs multi-user
CPU / laptop vs datacenter GPU
quantized GGUF vs accelerator-native formats
latency target vs throughput target
long shared prefixes
multi-GPU / distributed serving
09 · Measure the right thing

“Tokens per second” alone is not a serving benchmark.

TTFT

Time to first token. Dominated by queueing + prefill. Critical for perceived responsiveness.

ITL / TPOT

Inter-token latency or time per output token. Captures decode smoothness.

Throughput

Total tokens or requests served per unit time across the whole system.

Also track

P50/P95/P99 latencyqueue timeGPU utilizationKV usageOOM rateconcurrent sequences

The core trade-off

Optimizing for one user’s latency and optimizing total fleet throughput are not the same objective.

serving objective = quality × latency × throughput × cost × reliability

The one-page mental model

fit model→ quantize →move less memory→ FlashAttention →pack requests→ continuous batching →pack KV→ paging →skip decode steps→ speculation
