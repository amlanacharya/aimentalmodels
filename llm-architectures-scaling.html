LLM Architecture Families & Scaling

01 · Transformer families

Encoder, decoder, and encoder-decoder solve different problems

They share attention blocks, but differ in what information each token is allowed to see and what the model is trained to produce.

Encoder-only

Every token can usually attend bidirectionally to the whole input. Strong for representation learning, classification, embeddings, and token-level understanding.

input → contextual representation
BERT-likeembeddingsclassification

Decoder-only

Causal masking prevents a token from seeing future tokens. The model predicts the next token repeatedly.

prefix → next token → next token → …
GPT-likechatgeneration

Encoder-decoder

An encoder builds an input representation; a decoder generates output while cross-attending to that representation.

input → encoder memory → decoder → output
T5-liketranslationseq2seq
For modern chat LLMs, decoder-only is the dominant mental model. But encoder-only models remain excellent when you need representations rather than free-form generation.
02 · Capacity

Dense models activate everything. MoE models route selectively.

Dense

Every token passes through the same full set of feed-forward parameters in each layer.

Token→Attention→All FFN weights

Simple execution model; compute rises directly with model width/depth.

Mixture of Experts (MoE)

A router sends each token to only a small subset of expert feed-forward networks.

Token→Router→Top-k experts

More total capacity without activating every expert for every token.

A sparse MoE can hold many experts but activate only a few for each token.
MoE trades compute for systems complexity. You save per-token arithmetic relative to activating every parameter, but pay in routing, expert placement, load balancing, communication, and memory capacity.
03 · Parameter counts

Total parameters are not the same as active parameters

This distinction is essential when comparing dense and MoE models.

3.1%experts active per token
32×expert capacity vs active expert compute
memory-heavyserving implication

Illustrative expert-layer intuition only; real models also contain shared attention, embeddings, routers, and possibly shared experts.

Total parameters

How much learned capacity exists in the full checkpoint. This strongly affects storage and how much memory is needed to place weights.

Active parameters

How much of that capacity participates in one token's forward pass. This is more closely related to per-token arithmetic cost.

04 · Scaling laws

Bigger helps, but only if compute and data scale sensibly too

Scaling laws describe predictable relationships between model size, data, compute, and loss. The engineering lesson is not “always add parameters”; it is allocate a fixed compute budget intelligently.

Model size

More parameters can increase representational capacity, but larger models cost more to train, store, and serve.

Training data

More useful tokens expose the model to more patterns. An oversized model trained on too little data wastes capacity.

Compute

Training budget couples model size and token count. Chinchilla-style results emphasized that many earlier LLMs were undertrained for their size.

fixed training compute → choose a balanced model size + token budget
The key question is marginal return. If you have one more unit of compute, is it better spent on a larger model, more data, longer training, better data, or inference-time reasoning?
05 · Context scaling

Longer context is not free memory

A larger context window changes both attention work and KV-cache requirements. Architecture and kernel choices determine how painful that becomes.

Attention work

Naïve full self-attention compares token positions against other token positions, so training/prefill attention work grows roughly quadratically with sequence length.

attention interactions ∝ n²

Decode memory

During autoregressive generation, the KV cache grows roughly linearly with stored sequence length for a fixed architecture.

KV cache ∝ context × layers × KV heads × head dim
4×relative naïve attention interactions vs 4K
2×relative KV length vs 4K
manageablesystems pressure

Illustrative scaling ratios; optimized attention implementations reduce memory traffic but do not make sequence length irrelevant.

Long context is an architecture + serving problem. RoPE scaling, GQA/MQA, FlashAttention-style kernels, paged KV memory, retrieval, and context compression all exist because “just send more tokens” gets expensive.
06 · Reasoning models

Capability can scale at inference time too

Traditional scaling spends most extra compute before deployment. Reasoning-oriented systems can also spend additional compute per query through longer deliberation, search, verification, sampling, or tool use.

Prompt→More inference compute→Search / deliberate / verify→Answer
Scale axisYou spend more compute on…Main cost
Pretraining scaleMore parameters / tokens / training stepsUpfront training
Inference-time scaleMore generated reasoning, samples, search, verification, toolsLatency + serving cost per request
Reasoning performance is now partly a serving decision. A system can trade extra latency and tokens for harder-task accuracy, which means product SLOs and cost budgets become part of the reasoning architecture.

Architecture is an operational contract

A model checkpoint silently commits you to particular VRAM, bandwidth, interconnect, batching, KV-cache, and latency requirements. Model selection is therefore also infrastructure selection.

If you understand one sentence

Model architecture is how you decide where capacity lives and when compute is spent; scaling is the art of spending more compute where it buys the most capability.
