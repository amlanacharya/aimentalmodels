AI Systems Architecture & Orchestration

The 20% of architecture that explains 80% of production AI systems: where the model should make decisions, where deterministic software should take over, how tools and state fit together, and how to survive retries, timeouts, partial failures, and long-running workflows.

Mental model

The model is one component, not the application

A production AI system is a normal software system with a probabilistic decision-maker inside it. Reliability comes from surrounding that probabilistic component with deterministic contracts and controls.

Pareto rule: keep model judgment narrow; keep execution, validation, persistence, and recovery deterministic.

One sentence to remember

Models choose; software constrains and executes. The more consequential the action, the stronger the deterministic boundary should be.

Control flow

Workflow first. Agent only where uncertainty is useful.

A workflow follows a known graph. An agent decides parts of the graph at runtime. Most robust systems are hybrids.

Workflow

Use when the steps are known in advance.

A → B → C → approval → D
Best for: compliance flows, document pipelines, reconciliations, repeatable back-office processes.

Agent

Use when the next useful action depends on information discovered during execution.

observe → decide → tool → observe → decide …
Best for: research, investigation, open-ended troubleshooting, tool selection.
QuestionPrefer workflowPrefer agent
Do you already know the next step?YesNo
Can the path vary meaningfully?RarelyOften
Is auditability critical?Strong defaultUse constrained agent nodes
Could a wrong action be costly?Deterministic controlHuman/tool guardrails
Model boundary

The model gateway gives you one place to control model behavior

Do not scatter direct model calls throughout the codebase. Put model selection, timeouts, fallbacks, budgets, tracing, and policy in a thin gateway.

Routing

Choose model by task, latency, cost, context size, or capability.

Resilience

Timeouts, retries, fallback models, circuit breakers, and rate-limit handling.

Governance

Logging, redaction, prompt versions, token budgets, and usage attribution.

Pareto cut: every model call should be observable, budgeted, versioned, and recoverable.
Contracts

Never make downstream software parse prose if you can avoid it

Structured outputs turn a fuzzy language boundary into a typed software boundary. The model can still reason probabilistically, but the application receives a predictable shape.

Weak boundary

"I think we should refund the user and maybe contact finance."

Downstream code must interpret natural language.

Strong boundary

{ "action": "refund", "amount": 1200, "requires_approval": true }

Downstream code validates fields and executes only allowed actions.

Why this matters

Modern structured-output systems can constrain generation to a supplied schema, which is materially stronger than merely asking for “valid JSON.” [1]

Action boundary

The LLM should request a tool call, not perform the side effect itself

Treat the model's tool call as an intent proposal. Your runtime resolves permissions, validates arguments, executes the function, and records the result.

Model proposes→Validate schema→Check policy→Execute→Record result

Read tools

Search, fetch, inspect, calculate. Usually lower risk and easier to retry.

Write tools

Send, delete, transfer, publish, book. Require stronger authorization, idempotency, and often approval.

State

Memory is not one thing

Separate transient conversation context from durable application state. Otherwise every problem becomes “put more text in the prompt.”

State typeWhat it storesTypical home
Working contextCurrent instructions, recent observationsPrompt / context window
Workflow stateCurrent step, attempts, tool outputsDatabase / workflow engine
Domain memoryDocuments, entities, factsSearch / RAG / DB
User preferencesStable personalizationProfile store with policy controls
Audit stateWho did what, when, whyImmutable logs / event store
Rule: if the system must survive a process restart, it cannot live only inside the model context.
Durability

Retries are dangerous unless actions are idempotent

Distributed AI workflows fail halfway. A timeout does not tell you whether the remote side effect happened. Design every consequential step assuming it may run more than once.

Queue

Decouples slow or bursty work from request-response latency.

Retry

Re-attempt transient failures with backoff and bounded attempts.

Idempotency

Repeating the same request produces no duplicate side effect.

Critical insight: “retry the tool call” is not a reliability strategy unless the tool contract is safe to repeat.
Interoperability

MCP standardizes how AI applications connect to external capabilities

Model Context Protocol is best understood as an interoperability layer: clients discover and invoke tools/resources from servers through a shared protocol rather than every integration inventing its own model-facing contract.

AI application↔MCP client↔MCP server↔Service / data

The July 28, 2026 MCP specification moved to a stateless protocol core and added features including multi-round-trip requests, header-based routing, cacheable list results, and authorization hardening. [2]

Do not confuse MCP with an agent framework. MCP standardizes connectivity. Your application still owns orchestration, state, policy, approvals, retries, and business logic.
Observability

Trace the whole trajectory, not only the final answer

A bad final output may originate in routing, retrieval, model reasoning, a malformed tool call, a tool failure, stale state, or post-processing. Trace each boundary.

Trace per run

Prompt version, model, latency, tokens, retrieved evidence, tool arguments/results, retries, approvals, final outcome.

Metrics across runs

Success rate, escalation rate, cost/task, TTFT, tool error rate, retry rate, judge scores, business outcome.

trace_id → model_call → tool_call → retry → approval → result
Reliability

Put failure boundaries between probabilistic and irreversible steps

The model should be allowed to be uncertain without turning that uncertainty into an irreversible side effect.

Putting it together

The production blueprint

You can map almost every AI application onto this architecture.

Not every system needs every box. Start simple; add durability and controls when the failure mode justifies them.

Write tools are idempotent
Workflow state survives restart
