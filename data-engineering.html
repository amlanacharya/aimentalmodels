Module 04 · Data Engineering for AI Systems

Your model can only reason over the data pipeline you actually built.

AI data engineering is not “put files into a vector database.” It is the system that turns messy source data into trustworthy, refreshable, permission-aware representations for RAG, fine-tuning, agents, and evaluation.

The core pipeline

Raw data must become a governed representation

The useful mental model is a sequence of increasingly trustworthy transformations. Every step should be reproducible, observable, and reversible.

Sources→Ingest→Parse→Normalize→Enrich→Validate→Publish

Bronze

Keep the source as received: original file/event, source URI, timestamps, permissions, checksum.

Silver

Parsed and normalized content with stable schema, cleaned fields, IDs, metadata, and quality results.

Gold

Task-ready assets: chunks, labels, embeddings, retrieval indexes, training examples, eval sets.

Mental model: never make the vector index your source of truth. Keep a recoverable canonical layer upstream.
Data contracts

Define what “valid data” means before the model sees it

Schema contract

Required fields, types, nullable fields, identifiers, version, timestamps, language, source type.

document_id · source_uri · version · text · acl · updated_at

Semantic contract

What a field means, not only what type it has. “effective_date” and “uploaded_at” are both dates but answer different questions.

Why this matters

When contracts are explicit, a broken upstream parser becomes a failed pipeline run, not a mysterious hallucination two stages later.

Parsing & normalization

Preserve structure before you clean text

A parser should recover the document's information structure: headings, paragraphs, tables, lists, captions, page boundaries, section hierarchy, and coordinates when useful.

Parsing

PDF → blocks, HTML → DOM-aware sections, email → headers/body/attachments, audio → timestamped transcript, tables → rows/columns.

Normalization

Canonical encodings, whitespace, date formats, units, IDs, language tags, boilerplate removal, OCR cleanup.

Do not flatten too early. Once table cells, headings, or page relationships are discarded, downstream chunking cannot reconstruct them reliably.
Chunking

Chunk by information boundaries, not by an arbitrary token number

StrategyWorks well forMain risk
Fixed tokensSimple homogeneous textSplits semantic units
Recursive separatorsGeneral documentsStructure only partially preserved
Heading / section awarePolicies, reports, manualsVery large sections
Parent → childRAG requiring local precision + larger contextMore index/link complexity
Sentence / semanticDense proseExtra compute and unstable boundaries
Table-awareFinancial / operational dataNaive text serialization loses meaning
good chunk = locally retrievable + globally interpretable + traceable to source
Overlap is a patch, not a strategy. Use overlap when boundary loss is plausible; do not use huge overlap to compensate for poor structural parsing.
Metadata

Metadata is part of retrieval, not administrative decoration

Provenance

Source, author, document ID, section, page, version, ingestion run.

Filtering

Business unit, geography, product, date, content type, tenant, language.

Security

ACLs, sensitivity labels, tenant IDs, retention class, consent scope.

Retrieval principle: metadata filters can eliminate impossible candidates before semantic similarity ranking begins.
Deduplication

Duplicate knowledge quietly corrupts retrieval and evaluation

Copies, revised documents, email forwards, boilerplate, and near-duplicate web pages can overweight one idea and inflate benchmark results.

Exact duplicate

hash(canonical_bytes) → same hash = same object

Cheap and deterministic.

Near duplicate

Use normalized shingles, MinHash/LSH, edit similarity, or embedding similarity with conservative thresholds.

Versioning beats deletion. Keep lineage between superseded and current documents so answers can respect “as-of” time.

Lineage & reproducibility

Every answerable chunk should have an ancestry

chunk_id → parser_version → document_version → source_object → source_system

Also record the transformation configuration: chunker version, embedding model, index build, enrichment rules, and access-control snapshot.

Why lineage matters

Debug wrong answers, rebuild indexes, prove source provenance, replay old evaluations, satisfy audit questions.

Version the transformation

A document processed with parser v4 and chunker v7 is not operationally identical to the same bytes processed with v2/v3.

Embedding & indexing pipeline

Embedding is a derived-data job

Validated chunks→Embed→Attach metadata→Index→Smoke eval

Stable IDs

Use deterministic document/chunk IDs where possible so refreshes can upsert rather than blindly duplicate.

Model version

An index built with embedding model A is not safely mixed with vectors from model B unless the system explicitly supports that space.

Operational rule: treat embedding-model changes like schema migrations.
Batch vs streaming

Freshness requirements determine the ingestion architecture

BatchStreaming / event driven
Best forLarge document corpora, nightly refreshes, offline trainingTickets, transactions, conversations, changing operational state
ComplexityLowerHigher
FreshnessMinutes → daysSeconds → minutes
Failure modelRe-run partition/jobOffsets, retries, ordering, duplicates
Key propertyReproducibilityIdempotency
Default to batch unless the user experience actually requires streaming freshness.
Different AI workloads

RAG, fine-tuning, agents, and evals need different data products

RAG

Source-faithful chunks, metadata, ACLs, freshness, embeddings, lexical index, provenance.

Fine-tuning

High-quality input/output examples, deduplication, balanced behavior coverage, train/dev/test isolation.

Agents

Current operational state, tool schemas, event streams, durable state, permission-scoped records.

Evals

Representative tasks, stable labels/rubrics, slices, versioning, contamination checks, regression history.

Labels & synthetic data

Synthetic data is an amplifier, not a truth source

Synthetic examples can cheaply broaden coverage, create edge cases, or bootstrap labels. But they also reproduce the generator's blind spots and can create unrealistic distributions.

Real seed data→Generate variants→Validate / filter→Human spot check→Use selectively
Keep provenance. You should always know whether an example is human-labeled, model-labeled, heuristic, weak supervision, or synthetic.
Refresh & invalidation

The hard part is often deleting or replacing stale derived data correctly

Incremental refresh

Detect changed source version → invalidate affected chunks → regenerate embeddings → update indexes atomically.

Tombstones

If a source is deleted or access is revoked, derived chunks and vectors must stop being retrievable.

source change → impact set → rebuild derived assets → verify → publish new version
Freshness is a correctness property. A perfectly retrieved obsolete policy can still produce the wrong answer.
Production blueprint

A resilient AI data architecture

Lineage and metadata cut across the entire pipeline. The AI application consumes published data products, not raw sources directly.
What to remember

The AI data engineering 80/20

Keep raw/canonical data recoverable
Preserve document structure before chunking
Use stable IDs and explicit versions
Treat metadata as retrieval logic
Deduplicate before indexing and training
Validate permissions before publish
Measure parser and chunk quality
Version embedding/index transformations
Default to batch unless freshness requires streaming
Track lineage from source → chunk → vector → answer
Separate RAG, fine-tuning, agent, and eval data products
Invalidate stale or revoked derived data

If you understand one sentence

AI data engineering is the discipline of making model context reproducible, trustworthy, fresh, and traceable. Embeddings are only one derived representation inside that pipeline.
