Module 18 · Production operations

AI Observability, Reliability & Production Operations

How to know what happened, why it happened, how bad it is, and whether a change made the system better. The Pareto view of traces, metrics, SLOs, cost, releases, drift, and incident response for LLM, RAG, and agent systems.

01 · The operating model

Logs tell you events. Traces tell you journeys.

Classic observability still matters, but AI systems add non-deterministic model calls, retrieval, tools, retries, and multi-step trajectories. You need to correlate all of them.

Request→Retriever→Model→Tool→Response

Metrics

Aggregates: latency, error rate, tokens, queue depth, cache hit rate, tool success, cost.

Logs

Discrete events: retries, validation failures, auth denials, tool errors, deployment changes.

Traces

One request across spans so you can see which model, retriever, tool, or retry consumed time and money.

The practical rule: if a user says “the agent was slow,” you should be able to locate the exact slow span without reproducing the run manually.
02 · AI traces

Trace the semantic work, not just HTTP calls

A useful AI trace captures model generation, retrieval, tool execution, and agent steps as first-class operations.

The trace answers “where did time and failure come from?” in one view.
Span typeUseful attributes
Model callprovider/model, input/output tokens, latency, finish reason, retries
Retrievalquery, document IDs, scores, top-k, filter policy, latency
Tooltool name, arguments schema/version, auth scope, result status, latency
Agent stepstep number, chosen action, state/checkpoint ID, stop reason
03 · Version lineage

You cannot debug what you cannot reproduce

Every result should be attributable to the exact versions that produced it.

request → prompt_version + model_version + retriever_version + index_snapshot + tool_schema + policy_version

Why this matters

“The model got worse” may actually mean a prompt changed, a document index refreshed, a reranker version changed, or a tool schema broke.

Minimum lineage

Store immutable IDs for prompts, model configuration, datasets/indexes, tool contracts, feature flags, and deployment versions.

04 · SLIs & SLOs

An AI system needs user-facing reliability targets

GPU utilization is not an SLO. Choose indicators that correspond to what the user experiences.

LayerGood SLI examples
AvailabilitySuccessful requests / eligible requests
LatencyTTFT p95, end-to-end latency p95/p99, inter-token latency
Qualitytask success, groundedness, tool success, human escalation rate
RAGretrieval recall, empty-hit rate, stale-doc rate
Agentstrajectory success, retry budget exhaustion, checkpoint recovery success

SLO ≠ aspiration

An SLO should be measurable and attached to an error budget. Example: 99% of eligible requests complete successfully and 95% achieve TTFT under 2 seconds during a rolling window.

05 · Tail latency

Averages hide pain

In AI systems, a small number of slow tool calls, retries, long prompts, cache misses, or overloaded workers can dominate user experience.

1.45 sMean latency
1.0 sp95 latency
10.0 sp99 latency
Illustrative distribution: most requests take ~1 s, slow-tail requests take ~10 s. The mean can still look acceptable while the tail is painful.
Operate on p95/p99, not just averages. Queue depth, retries, cold starts, long context, tool latency, and network transfers often show up first in the tail.
06 · Cost observability

Token counts are a production metric

AI cost is driven by more than request volume. Prompt length, output length, retries, tool loops, cache reuse, model routing, and multimodal inputs all matter.

cost/request ≈ model tokens + embeddings/retrieval + tool/API cost + retries + infrastructure share

Track per request

Input/output tokens, cached tokens, model used, retries, tool calls, GPU time, external API spend.

Track per feature

Cost per successful task, not merely cost per token. Cheap failures are still waste.

Track outliers

Long-context prompts and runaway loops can produce extreme cost tails even when averages look healthy.

08 · Safe releases

Do not flip the whole fleet at once

Shadow

Run a candidate in parallel without affecting users. Compare outputs, cost, and latency.

Canary

Send a small slice of real traffic to the new version and watch guardrail metrics.

Rollback

Keep prompt/model/tool/index versions independently reversible. Fast rollback beats heroic debugging.

Offline eval→Shadow→Canary→Ramp→Full rollout
Release gates should include quality, latency, cost, and safety. A candidate can improve benchmark quality while violating a latency or cost SLO.
09 · Drift & feedback

Production is an ongoing experiment

Monitor changes in inputs and outcomes, but close the loop with evaluation. Drift alone does not prove quality degradation.

Production traces→Failure slices→Curated eval cases→Regression suite→Release

Monitor distributions

Topic mix, input length, language, tool mix, retrieval score distributions, model routing, user segments.

Monitor outcomes

Task success, human corrections, escalations, abandonment, cost per success, incident rate.

10 · Incident response

AI incidents need reproducible evidence

When a production failure matters, preserve the request lineage and the exact system state before changing anything.

Freeze trace + request ID
Capture prompt/model/tool/index versions
Identify first bad span
Check whether issue is systemic or a slice
Mitigate: feature flag, route, rollback, disable tool
Add the failure to regression evals

Postmortem principle

Do not stop at “the model hallucinated.” Ask which control failed to prevent, detect, contain, or recover from the bad behavior.

What to remember

The observability 80/20

Trace model, retrieval, tool, and agent spans together
Attach immutable version lineage to every run
Track p95/p99, not just mean latency
Measure cost per successful task
Use SLOs tied to user experience
Separate failure classes before debugging
Shadow and canary risky changes
Keep rollback paths independent
Convert production failures into eval cases
Treat observability content as sensitive data

If you understand one sentence

Production AI is observable only when every output can be traced back to the exact model, context, retrieval, tools, policies, and execution path that produced it.
